# 版本命名规范（1.0 线）

> 定稿：2026-11-07（用户拍板）。**这条规则只描述 1.0 及以后**；0.9.x 历史版本号不改、
> 不重打，文档里出现的旧号保留原样。
> 2026-11-08 增补 **RC 渠道**：对外号（RC1/RC2…）与内部四段号**各自独立递增**，
> 内部号永不回退（`1.0.0.15 → 1.0.0.16 → …`）。
> 唯一来源是 `src/common/version.h`；`tools/version.py` 负责读写与派生，其它地方一律不手写版本号。

## 1. 规则总表

| 场景 | 文件名 | 界面显示 | 内部四段（FILEVERSION / version.json / 载荷戳） |
|---|---|---|---|
| 测试版 | `九转大还原1.0-beta.N.exe` | `1.0 beta.N` | `1.0.0.N` |
| RC 版 | `九转大还原1.0-rc.N.exe` | `1.0 RCN` | **继续递增**（如 `1.0.0.15`、`1.0.0.16`） |
| 正式版 | `九转大还原1.0.0.exe` | `1.0.0` | 待定（用户权衡"1.0.0.0"或继续递增） |
| 正式版之后修 bug | `九转大还原1.0.1.exe` 起 | `1.0.1` | `1.0.1.0` |

字段含义（`src/common/version.h`）：

| 宏 | 含义 | beta 期间 | RC 期间 | 正式版 |
|---|---|---|---|---|
| `SYSRECOVER_MAJOR` | 主版本 | 人指定（1） | 同左 | 同左 |
| `SYSRECOVER_MINOR` | 次版本 | 人指定（0） | 同左 | 同左 |
| `SYSRECOVER_PATCH` | 第三位：正式版之后修 bug 递增 | **固定 0** | **固定 0** | 0,1,2,3... |
| `SYSRECOVER_BETA` | 第四位：发布计数器，每出一次包 +1 | 1,2,3... | 15,16,17...（**不回退**） | **0** |
| `SYSRECOVER_RC` | RC 渠道号（0 = 不是 RC） | 0 | 1,2,3...（**对外号**） | 0 |

约定：

- **文件名不带空格**（空格在批处理 / 命令行 / 下载器上要额外加引号）；界面文案可以带空格。
- beta / RC 只是**渠道标记**，不进数字段，所以四段永远是纯十进制数字，属性页与版本比较都能正常工作。
- **两套计数**：对外 RC 号每出包 +1；内部第四段每出包也 +1，但从不重置。出包报告必须写明
  对应关系（例："对外 1.0 RC2 ↔ 内部 1.0.0.16"）。
- 第三位留给正式版之后的 1.0.1 / 1.0.2，**beta / RC 期间不许占用**（`tools/version.py --check` 会拒绝）。
- RC 期间第四个段不能为 0（否则与正式版撞号，`--check` 拒绝）。
- 同版本号**不覆盖旧包**：`tools/portable-pack.py` 在写文件前检查目标是否存在，存在就拒绝并提示
  先递增发布号（`tools/version.py --bump`）。

## 2. 衔接关系

- `0.9.96 → 1.0 beta.1`：本线起点（2026-11-07），0.9.x 的历史发布号不追认、不改写。
- 已打出的旧包 `D:\九转大还原1.0.0-beta.1.exe` 按本规则记为 **`1.0 beta.1`**，
  只把文件名规范成 `九转大还原1.0-beta.1.exe`，**不重新构建**；它内含的救援载荷与
  `dist\bootfiles` 基线一致（initramfs 17,407,298 字节）。
  ⚠️ 该包内的版本资源串仍是旧写法 `1.0.0-beta.1`（非纯数字），属性页会照原样显示；
  这是"不重建"的代价，仅影响这一份历史包，新出的包一律为四段纯数字。
  同一内容另有两份带日期后缀的历史备份（`-20261107` / `-20261107-before-delwrite`），
  仅作追溯，不再对外发出。
- 正在改造的这一版出包即 **`1.0 beta.2`**（内部 `1.0.0.2`）。

## 3. 已知副作用：正式版四段会"回落"

正式版 `1.0.0.0` 的四段数字**小于**最后一个 beta（例如 `1.0.0.8`），属性页看起来像"变旧"。
这是 beta 号占第四段必然的结果：**仅影响观感**。产品没有自动更新机制，
版本判定按**文件名与渠道字段**（`SYSRECOVER_BETA`），不靠数字大小比较。
后续若引入更新检查，必须先比渠道再比发布号。

## 4. 改号与出包

```bat
python tools/version.py --check      :: 校验四段/显示串一致性
python tools/version.py --bump       :: 内部第四段 +1（写回 version.h，可提交）
python tools/version.py --rc N       :: 切 RC 渠道并指定对外 RC 号（内部四段不动）
python tools/version.py --release    :: 切正式版（beta=0，RC=0）
python tools/version.py --patch N    :: 正式版之后：第三位 = N
python tools/version.py --filename   :: 打印本次发布文件名
mingw32-make -f Makefile release     :: 一步出包：递增 → 双架构构建 → 打包 → SHA256
```

`make release` 的顺序固定为：`--bump` → `package`（x64 + x86 + 共享资源）→ `portable`
（单文件并复制到 `D:\九转大还原<版本>.exe`）→ `dist\SHA256SUMS.txt` → `--check`。

## 6. 正式版口径（2026-11-08 用户定稿；现在只记录，不提前改代码）

- 对外/界面：`1.0.0`（三段）。**exe 文件属性不展示第四位编辑次数**（四段时补 `.0`）。
  文件名 `九转大还原1.0.0.exe`。
- 内部构建号继续四段递增（`1.0.0.15`、`1.0.0.16`…），**只**出现在
  `version.json`、`dist\bootfiles\rescue-build.txt`、initramfs 内戳
  （`zjrescue-version`）、救援回执与日志里，供排障/批次追溯，**不对外展示**。
- RC 包：对外 `RC1`/`RC2`…；文件属性可带编辑次数以便区分批次。
- 已知取舍（用户确认接受）：正式版属性数字会小于最后一版 RC（如 `1.0.0.0` vs `1.0.0.16`），
  **属有意选择，不作为缺陷**；升级判定永远先比渠道（beta/RC/正式）再比数字。
- **`version.json` 保留四段内部号**：`tools/check-dist.py` 与 `check-shell.py` C7 的三元
  一致校验（version.json / rescue-build.txt / initramfs 内戳）都按四段比对；
  只把**展示层**降到三段即可，无需改动校验。若未来把 version.json 改成三段，会直接
  打破"四处一致"门禁，需同步改三道校验与打包脚本——不建议。
  仅当三处口径冲突时才需介入；目前**不冲突**：`SYSRECOVER_DISPLAY` 只影响界面/文件名，
  与四段校验字段相互独立。

## 5. 三处同步（门禁）

`version.json`、`dist\bootfiles\rescue-build.txt`、initramfs 内的 `zjrescue-version`
必须与 `SYSRECOVER_VERSION` 一致：

- `make package` 时由 `$(VERSION)` 写入前两处；
- initramfs 由 `tools/build-debian-rescue.py` 在构建时写内戳（`version.h` 变化会自动触发重建）；
- `tools/check-dist.py` 与 `tools/check-shell.py`（C7）断言三者同源，不一致就拒绝打包。
