# 已知问题与限制（1.0.0 测试版）

> 适用版本：`1.0.0-beta.1`（界面显示「1.0.0 测试版」，英文 `1.0.0 Beta`）。
> 本文只列**已确认、无法在发布前消除**的问题；待修项与逐条门禁状态见
> `docs/26-公开前准备与1.0观察期.md` §2 与 `docs/34-发布门禁总表.md`。

**这一版是测试版**：所有二进制**没有代码签名**，也**没有在实机上跑通完整的备份/还原闭环**
（自动化测试与虚拟盘验证见 `docs/BUILD-REPORT.md` / `docs/07`）。请只在不重要的机器或虚拟机里试用。

## 1. 未签名 / SmartScreen / 杀软误报

- **发布物没有代码签名证书**。首次运行 `SysRecoverUI.exe` 或单文件版时，
  Windows 10/11 可能弹出「Windows 已保护你的电脑」（SmartScreen）。
  - 处理：点「更多信息」→「仍要运行」。
  - 校验：下载后先用 `dist/SHA256SUMS.txt` 核对 SHA256（见 §2），确认文件未被篡改再运行。
- **签名策略（2026-11 定稿）**：只走**免费渠道**，不为发布采购付费代码签名证书。
  因此**当前发布物一律按"未签名"口径说明**——SmartScreen 提示属预期行为，不是故障。
  将来若拿到免费签名，发布顺序**必须**是：
  1. 先出全部产物：`make package` 后 `make portable`（单文件按约定放 `D:\` 根，见 Makefile 注释）；
  2. 再对**外层 exe**（`九转大还原<ver>.exe`、以及解压后的 `SysRecoverUI.exe` 等）签名；
  3. **最后**执行 `make sha256` 重新生成 `SHA256SUMS.txt`。
  顺序颠倒（先算哈希再签名）会让哈希与发行文件对不上，比不签名更糟。
- 部分安全软件（360、金山毒霸等）可能拦截以下行为并弹窗：
  - 写 UEFI 启动项（`Boot####` / `BootOrder` / `BootNext`）；
  - 用 `diskpart` / `format` / `mkntfs` 格式化目标分区；
  - 安装启动菜单、写 `BootNext` 做一次性引导。
  这些都是产品功能所需；**被拦截时暂存会中止并给出提示**，不会静默继续。
- **不要为了运行而关闭系统安全软件**；如果被拦截，先加信任/白名单，再重试。

## 2. 校验下载文件（SHA256）

```powershell
# 在 dist 目录执行（发布包自带 SHA256SUMS.txt）
Get-FileHash .\SysRecoverUI.exe -Algorithm SHA256
# 与 SHA256SUMS.txt 中对应行比对；不一致就不要运行
```

## 3. 体积与运行环境

- `dist/` 目录版解压后约 **52 MB**（含救援内核、initramfs、引导资产、双语词典、皮肤）。
  单文件版经压缩后通常更小；`Drivers/` 为用户自备驱动目录，不计入上述体积。
- **不做 32 位 CPU 的"原生系统还原"**：产品提供 x86 兼容入口（`*_x86.exe`），
  但 Linux 救援层固定 **x86_64**；纯 x64 PE（无 WOW64）请直接运行 `x64\SysRecoverUI.exe`。
- 只支持 **Windows 7 x64 及以后**（Win7 需 UCRT，随包提供）。Vista/2003/XP 不支持。
- 镜像文件必须放在**本机可访问的本地分区**：救援层不加载网络驱动，访问不到网络共享。

## 4. 功能边界

- 目前只读写 **WIM / ESD**（以及本产品的加密镜像 `.zje`）；不直接支持 GHOST/SNA/TBI 等格式。
- 异机还原只覆盖**内置的常见存储/输入驱动**（约 494 个 Linux 侧模块 + `Drivers/` 注入）；
  服务器阵列卡、特殊 OEM 设备可能仍需手动补驱动。
- `keep` 模式还原要求目标 NTFS 根目录能被完全清空；清不干净会在 apply 前中止
  （`step=wipe-incomplete`），这是**有意为之**（避免把盘写坏）。
- 引导修复失败时结果为 `result=OK_BOOT_UNFIXED`（系统已还原、引导未修好），
  Windows 侧不会显示"完全成功"；需要再用「修复引导」或手动处理。
- BitLocker 加密卷、EFS 加密文件、第三方重解析点等特殊内容未做专项兼容验证；
  操作前请先解密/备份。

## 5. 需要实机确认的 7 项

这些项目已通过纯逻辑测试或脚本回归，但**尚未在真机/VM 全链验收**，发布前建议逐项确认：

1. 救援层按磁盘序列号 + 分区 GUID 挑中目标盘（多盘同型号环境）。
2. keep 模式清空不完整时确实在 apply 前中止，且目标盘仍可挂载（`docs/07` §6 ④）。
3. 追加（append）中途失败/断电后，原镜像仍可校验通过（`docs/07` §6 ③）。
4. 引导修复失败时回执为 `OK_BOOT_UNFIXED`，Windows 侧不报"还原成功"。
5. USB 固定盘在勾选「显示 USB 设备」后可见、且标注正确；默认仍隐藏。
6. 高核数（≥16 核）机器备份时线程数被限制在 8，峰值内存可控。
7. NVRAM 写保护/写满时，临时 UEFI 启动项清理失败能被上层感知（退出码 1）。

### 5.2 QQ 复现路径实机证据（2026-11-06）

复现路径：**「安装到启动」菜单模式 → 重启 → 不按 F10（负向）/ 按 F10 选 SysRecover（正向）**。

1. **安装菜单**：GUI「文件>系统」页选镜像 + 目标 C:，Alt+N →「扫描后安装」。
   状态栏回显「启动还原菜单已安装：开机按 F10 选「SysRecover」即可还原该镜像」；
   标记文件 `logs\menu-install.txt` 记录 `time=2026-11-06 13:54:57`。

   —— 说明菜单不改系统 BCD，而是写 ESP 并注册 EFI 启动项。
2. **负向（不按 F10）**：重启后 Windows 正常进桌面；再启动程序，弹出「还原菜单未执行 /

   —— 新增的"自证"提示能正确识别"没进去"。**通过**。
3. **正向（按 F10）**：F10 打开固件 Boot Manager，列表含独立项 `SysRecover`；选中后进入救援层，

附注：本次正向测试用的是"仅含 `Windows\System32\winload.exe/.efi`"的合成镜像，还原后系统盘被替换，
重启报 `0xc000000f`（`\Windows\system32\config\system` 缺失）。这是**合成镜像本身不含系统注册表**
的必然结果，不是还原链路缺陷；但也暴露出"安装源类镜像（如 install.esd）被当作可还原系统镜像"
的误判风险 —— 已在还原前增加目录表预检（见 `docs/07` 与对应提交）。

### 5.3 待确认的故障注入方案（第 2/3/7 项，2026-11-06）

统一前提：每次注入前 `vmrun revertToSnapshot ... pre-restore-20261106` 或 `clean-20261106-b`；
**未拍快照不注入**。判定用的日志位置：救援层 `zjrestore-debug.log` / 控制台 `say` 输出、
程序 `logs\*.log`、`%ProgramData%\SysRecover\boot-cleanup.log`。

#### 第 2 项：keep 模式清空不完整 → apply 前中止

- **注入**：目标选非系统 NTFS 分区（本 VM 为 `p4` 99.8 GB），勾选"保留文件系统"（`target_mode=keep`）。
  用一份**测试版救援 initramfs**，在 `zjrestore-lite.sh` 第 1341 行 `rm -rf` 之后加一行
  `touch /tmp/zj_wipe/_zj-injected-leftover`（模拟"有文件删不掉"），重新打到 `bootfiles/`
  并安装菜单，然后重启进救援。该改法只动测试产物，不进仓库。
- **判定**：救援日志出现 `ERROR: target root NOT empty after wipe -> abort before apply`、
  `STEP=wipe-incomplete`、`exit 1`，且**没有** `wimlib-imagex apply` 行；目标分区回到 Windows 后仍能挂载、
  原 NTFS 未被 `mkntfs` 触碰（分区 UUID/序列号不变）。
- **复原**：回滚快照；恢复 `bootfiles/` 原 initramfs 并重装菜单。
- **备选（不改脚本）**：在目标根造"两轮都删不掉"的对象（自引用 junction / 特殊重解析点），
  但 ntfs3 与 ntfs-3g 行为不一致，成功率不可控，仅作兜底。

#### 第 3 项：append 中途断电 → 原镜像仍可校验

- **注入**：先在 `D:\zjesc\base.wim` 做一份基线镜像（中等源，压缩 fast）；再用
  `backup --dest D:\zjesc\base.wim --append --source <较大目录>` 追加第二个映像，在进度约 50% 时
  `vmrun stop <vmx> hard`（等价断电）。
- **判定**：重启后对 `base.wim` 跑 `verify`：应 rc=0 且**原有映像完整**（映像数仍为 1，或追加映像
  不出现半成品条目）；同时 `ImageQuickPrecheck` 仍能识别该镜像。若出现"原镜像校验失败"或
  "追加映像以半成品存在"，即判**失败**并回修代码队列。
- **复原**：回滚快照（镜像与临时目录一并消失）。

#### 第 7 项：NVRAM 写保护/写满 → 清理失败返回 1

- **注入**：以管理员在 guest 用 P/Invoke `SetFirmwareEnvironmentVariableW`（厂商 GUID 为全局变量 GUID，
  变量名用 `ZjFillNNNN`）逐条写入 1 KB 假变量，直到返回失败（写满）。随后正常走首启清理
  （Startup 里的 `SysRecover-RestoreBoot.cmd` → `zj-restore-boot.exe`），让 `RemoveUefiEntry` 写
  `BootOrder`/`DeleteVar` 失败。
- **判定**：`zj-restore-boot.exe` 退出码 **1**；`boot-cleanup.log` 出现
  `ERROR: write BootOrder failed (NVRAM read-only/full?)`、`uefi temporary entry removal FAILED`、
  `restore-boot cleanup done (..., ok=0)`；`BootOrder` 与临时 `Boot####` 仍在（可 `bcdedit /enum firmware` 复核）。
- **复原**：逐条删除 `ZjFillNNNN` 假变量（若写满导致删不动，直接回滚快照）；确认 `BootOrder` 完整后重启一次。
- **风险与已知缺口（已修复）**：写满 NVRAM 有极小概率影响固件启动项写入，必须用快照兜底。
  0.9.96/初版 1.0 的 `WriteDoneMarker()` 在 `ok=false` 时也写 `boot-cleanup.done`，Startup 的 cmd
  只看 marker 不看结果 —— 失败被静默吞掉。1.0 已改为：marker 带结果（`ok=1` / `ok=0`，
  契约集中在 `src/boot/cleanup_marker.h`），cmd 只在 `ok=1` 时自删，`ok=0` 时保留 cmd/helper
  到下次登录重试，同时 helper 弹一次可感知的失败提示；退出码仍为 1。单测覆盖
  `ok=1`/`ok=0`/旧 `done`/空文本四种标记与 cmd 模板（`tests/unit_tests.cpp`）。

## 5.4 早期入口标记 `entry-started`（2026-11-06）

**背景**：用户明确确认"按了 F10、选了 `SysRecover`"，仍然静默回到 Windows，且我们侧看不到
任何记录。原提示把"无救援回执"当成"没选菜单"，属于误判，已改文案；但"无日志"本身不能
区分三种情况：固件没加载 → 内核没起来 → 内核起来但卡在后段。

**实现**（`bootfiles/alpine/init`，initramfs 内 `/init`）：在加载存储模块之后、动任何分区之前，
扫描 vfat 分区并找到含 `EFI/ZJRESTORE` 的 ESP，向 `EFI/ZJRESTORE/entry-started.txt` 追加一行：

```
YYYY-MM-DD HH:MM:SS entry-started kernel=<uname -r> build=<zjrescue-version> boot=<boot_id>
```

只保留最近 50 行（ESP 空间紧）；每一步失败都静默跳过，**不阻塞启动**。

**判读口径**：
- 没有这一行 → 固件没有加载我们的 EFI，或内核没起来；
- 有这一行、没有后续救援日志 → init 起来了，卡在挂载/找镜像/日志落盘阶段（日志只落内存时
  会随重启丢失，这正是"完全没记录"的另一种来源）。

**局限**：这是"内核起来之后"的标记，仍不能把"固件跳过"和"内核崩溃"分开；要三态需要自建
EFI shim（写 ESP 标记后再 `LoadImage` 内核），按决定**暂缓**，等确有必要再评估。

**产物说明**：本次重打包 `bootfiles/initramfs-zjrestore.cpio.gz` 时发现它落后于源码
（`init` / `zjrestore-lite.sh` / `zjswap.sh` 三处均为旧版），已同步为当前源码内容。
另注意：`make all` **不会**刷新 `dist/bootfiles/`（那段拷贝在 `package` 目标里），
所以发布前必须执行 `make package`，否则安装器仍会装出旧救援层。

## 5.5 F10 后只有一根不闪的短横线、按键无响应（P0-2，2026-11-06）

**用户证词**：0.9.96 装菜单成功 → 重启按 F10 → 一根不闪的短横线，按键全部无响应，只能重启；
同一台机器用「重启进入固件」→ 固件启动菜单里选 `SysRecover` → 救援层完全正常，能还原系统。

**结论：未能复现**（VMware 17.6.1 / UEFI 环境下两条路径都正常），且现有现场证据不足以判定
短横线由谁画出。下面把"已证实"与"还缺什么"分开列出，**不以推测结案**。

### 已证实（可复核）

1. **条目字段无差异**。宿主机（Gigabyte B760M DS3H DDR4 / AMI F20）固件里 0.9.96 写入的
   `Boot0000` 实测：`attr=0x1`、`desc="SysRecover"`、`FilePathListLength=124`、
   `path=\EFI\ZJRESTORE\vmlinuz-zjrestore.efi`、`OptionalData=92 字符`
   （`initrd=\EFI\ZJRESTORE\initramfs-zjrestore.cpio.gz console=tty0 nvme_core.io_timeout=1 zjre=1`）、
   `BootOrder=0001 0000`（SysRecover 在末尾）。与当前源码常量（`kKernelPath` / `kCmdLine` /
   `attr=1` / BootOrder 末尾追加）逐字段一致 —— **不是"0.9.96 写坏了条目参数"**。
2. **该宿主机自 09:25 开机后没有重启**（`LastBootUpTime` 与系统日志 `6005/12` 均无今日重启记录），
   ESP 上有 0.9.96 载荷（`rescue-build.txt=0.9.96`，16:35:36），但没有 `entry-started.txt`、
   没有救援日志 → **这条目在本机从未被真正引导过**，所以本机不可能产生用户描述的"短横线"。
3. **0.9.96 的救援 `init` 没有 `entry-started` 标记**（该标记是本次才加的）。
   因此即使用户机器上能拿到 ESP，也无法用该标记回溯判定这次历史事件；分水岭只对**新载荷**有效。
4. **VM 复现（同一 17.6.1 / UEFI / 单 NVMe / ESP 100MB）**：
   - 用新载荷 + 与 0.9.96 字节相同的条目（338 字节，FPL=124，optchars=92）写入 `Boot0005`；
   - 按 F10 → 固件 `Boot Manager` 列表出现 `SysRecover`（Device Path 与写入值一致）；
   - 选中后内核正常输出、2.6 秒后写入 `EFI\ZJRESTORE\entry-started.txt`
     （`entry-started kernel=6.12.107+deb13-amd64 build=0.9.92 boot=…`，18:14:22）；
   - 全程没有短横线，按键正常（↓ 移动、Enter 选择均生效）。
   **结论：未能复现用户现象。**
5. 顺带复现出一个**相关但不同**的失败态：把 `BootNext` 指向一个**固件已删除的无效 `Boot####`** 时，
   VMware EFI 会停在开机 Logo、按键无响应（只能强制断电）。这说明"失效条目"会让固件卡住，
   但它不是用户描述的"一根短横线"。

### 为什么判不了"短横线是谁画的"

- 该现场用的是 0.9.96 载荷，本就没有 `entry-started` 标记，分水岭法无法回溯；
- 宿主机上的条目从未被引导（见上），拿不到"这次启动"的 `vmware.log` 与画面；
- 用户所说"按 F10"与"固件菜单里选 SysRecover"若都在同一个固件菜单里，两者应等价；
  现在唯一能确定的差异是"按哪个键 / 从哪条路径进入固件"。

### 还缺的证据（拿到任意一条即可继续）

1. 出问题的机器是哪一台、什么时间重启（宿主机自 09:25 未重启，VM 当前分支也没有该条目）；
2. 按键卡住那一刻的整屏截图（含四角）；
3. 同一目录的 `vmware.log`（若是实机，请给机型与 BIOS 版本）；
4. 重启回 Windows 后再导一次 `diag.txt`，看 `uefi boot entry` / `bootorder` 段；
5. 若方便，用新载荷重装菜单再试一次：新载荷会写 `entry-started.txt`。
   有该行 = 内核/init 起过；没有 = 更靠前就挂了。
