# 已知问题与限制（1.0.0 测试版）

> 适用版本：`1.0.0-beta.1`（界面显示「1.0.0 测试版」，英文 `1.0.0 Beta`）。
> 本文只列**已确认、无法在发布前消除**的问题；待修项见 `docs/26-公开前准备与1.0观察期.md` §2。

**这一版是测试版**：所有二进制**没有代码签名**，也**没有在实机上跑通完整的备份/还原闭环**
（自动化测试与虚拟盘验证见 `docs/BUILD-REPORT.md` / `docs/07`）。请只在不重要的机器或虚拟机里试用。

## 1. 未签名 / SmartScreen / 杀软误报

- **发布物没有代码签名证书**。首次运行 `SysRecoverUI.exe` 或单文件版时，
  Windows 10/11 可能弹出「Windows 已保护你的电脑」（SmartScreen）。
  - 处理：点「更多信息」→「仍要运行」。
  - 校验：下载后先用 `dist/SHA256SUMS.txt` 核对 SHA256（见 §2），确认文件未被篡改再运行。
- **签名策略（2026-11 定稿）**：只走**免费渠道**，不为发布采购付费代码签名证书。
  因此**当前发布物一律按"未签名"口径说明**——SmartScreen 提示属预期行为，不是故障。
  将来若拿到免费签名，发布顺序**必须**是：
  1. 先出全部产物：`make package` 后 `make portable`（单文件按约定放 `D:\` 根，见 Makefile 注释）；
  2. 再对**外层 exe**（`九转大还原<ver>.exe`、以及解压后的 `SysRecoverUI.exe` 等）签名；
  3. **最后**执行 `make sha256` 重新生成 `SHA256SUMS.txt`。
  顺序颠倒（先算哈希再签名）会让哈希与发行文件对不上，比不签名更糟。
- 部分安全软件（360、金山毒霸等）可能拦截以下行为并弹窗：
  - 写 UEFI 启动项（`Boot####` / `BootOrder` / `BootNext`）；
  - 用 `diskpart` / `format` / `mkntfs` 格式化目标分区；
  - 安装启动菜单、写 `BootNext` 做一次性引导。
  这些都是产品功能所需；**被拦截时暂存会中止并给出提示**，不会静默继续。
- **不要为了运行而关闭系统安全软件**；如果被拦截，先加信任/白名单，再重试。

## 2. 校验下载文件（SHA256）

```powershell
# 在 dist 目录执行（发布包自带 SHA256SUMS.txt）
Get-FileHash .\SysRecoverUI.exe -Algorithm SHA256
# 与 SHA256SUMS.txt 中对应行比对；不一致就不要运行
```

## 3. 体积与运行环境

- `dist/` 目录版解压后约 **52 MB**（含救援内核、initramfs、引导资产、双语词典、皮肤）。
  单文件版经压缩后通常更小；`Drivers/` 为用户自备驱动目录，不计入上述体积。
- **不做 32 位 CPU 的"原生系统还原"**：产品提供 x86 兼容入口（`*_x86.exe`），
  但 Linux 救援层固定 **x86_64**；纯 x64 PE（无 WOW64）请直接运行 `x64\SysRecoverUI.exe`。
- 只支持 **Windows 7 x64 及以后**（Win7 需 UCRT，随包提供）。Vista/2003/XP 不支持。
- 镜像文件必须放在**本机可访问的本地分区**：救援层不加载网络驱动，访问不到网络共享。

## 4. 功能边界

- 目前只读写 **WIM / ESD**（以及本产品的加密镜像 `.zje`）；不直接支持 GHOST/SNA/TBI 等格式。
- 异机还原只覆盖**内置的常见存储/输入驱动**（约 494 个 Linux 侧模块 + `Drivers/` 注入）；
  服务器阵列卡、特殊 OEM 设备可能仍需手动补驱动。
- `keep` 模式还原要求目标 NTFS 根目录能被完全清空；清不干净会在 apply 前中止
  （`step=wipe-incomplete`），这是**有意为之**（避免把盘写坏）。
- 引导修复失败时结果为 `result=OK_BOOT_UNFIXED`（系统已还原、引导未修好），
  Windows 侧不会显示"完全成功"；需要再用「修复引导」或手动处理。
- BitLocker 加密卷、EFS 加密文件、第三方重解析点等特殊内容未做专项兼容验证；
  操作前请先解密/备份。

## 5. 需要实机确认的 7 项

这些项目已通过纯逻辑测试或脚本回归，但**尚未在真机/VM 全链验收**，发布前建议逐项确认：

1. 救援层按磁盘序列号 + 分区 GUID 挑中目标盘（多盘同型号环境）。
2. keep 模式清空不完整时确实在 apply 前中止，且目标盘仍可挂载（`docs/07` §6 ④）。
3. 追加（append）中途失败/断电后，原镜像仍可校验通过（`docs/07` §6 ③）。
4. 引导修复失败时回执为 `OK_BOOT_UNFIXED`，Windows 侧不报"还原成功"。
5. USB 固定盘在勾选「显示 USB 设备」后可见、且标注正确；默认仍隐藏。
6. 高核数（≥16 核）机器备份时线程数被限制在 8，峰值内存可控。
7. NVRAM 写保护/写满时，临时 UEFI 启动项清理失败能被上层感知（退出码 1）。

### 5.1 实机验收记录（2026-11-06）

环境：VMware Workstation 17.6.1，UEFI，4 vCPU，单块 VMware Virtual NVMe（100 GB，GPT：
p1 ESP 100 MB / p2 100 MB / p3 NTFS 100 GB「C: 当前系统」/ p4 NTFS 99.8 GB）。
快照：`pre-restore-20261106`、`clean-20261106-b`（所有写盘动作前均已拍快照）。

| # | 项目 | 判定 | 依据 / 原因 |
|---|------|------|-------------|
| 1 | 多盘同型号按序列号 + 分区 GUID 挑盘 | **无法判定** | 本 VM 只有 1 块盘，无"同型号双盘"环境 |
| 2 | keep 模式清空不完整需在 apply 前中止 | **无法判定** | 需故障注入（造"删不掉的残留文件"）；代码侧已确认 `zjrestore-lite.sh` 在 apply 前有中止分支（`STEP=wipe-incomplete` / `wipe-not-mountable`，exit 1） |
| 3 | append 中途失败/断电后原镜像仍可校验 | **无法判定** | 需断电/中断注入，未做 |
| 4 | 引导修复失败回执 `OK_BOOT_UNFIXED`，Windows 侧不报成功 | **无法判定** | 本 VM 为 UEFI，救援日志明确 `no bootfix needed (UEFI boot), skip boot files`、`UEFI/GPT: ESP untouched, skip PBR/boot-region repair`，走不到 PBR 修复失败分支；需 BIOS 机型 |
| 5 | USB 固定盘勾选后可见、默认隐藏 | **无法判定** | VM 无物理 USB 设备可挂载 |
| 6 | ≥16 核时线程数被限 8 | **无法判定（待补测）** | 当前 4 vCPU，备份日志为 `threads=4 (cap 8)`；需把 `numvcpus` 改为 16 后重启再判 |
| 7 | NVRAM 写保护/写满时清理失败可感知（退出码 1） | **无法判定** | 无 NVRAM 写保护/写满的注入条件 |

结论：七项中**没有出现"失败"**，但也**没有一项可以判定为"通过"** —— 1/5 是环境不满足，2/3/7 需故障注入，
4 需 BIOS 机型，6 需改配置重启。上述"无法判定"均为环境/注入条件缺失，不是产品缺陷。

### 5.2 QQ 复现路径实机证据（2026-11-06）

复现路径：**「安装到启动」菜单模式 → 重启 → 不按 F10（负向）/ 按 F10 选 SysRecover（正向）**。

1. **安装菜单**：GUI「文件>系统」页选镜像 + 目标 C:，Alt+N →「扫描后安装」。
   状态栏回显「启动还原菜单已安装：开机按 F10 选「SysRecover」即可还原该镜像」；
   标记文件 `logs\menu-install.txt` 记录 `time=2026-11-06 13:54:57`。
   `bcdedit /enum` 安装前后**完全一致**（默认 `{current}` → C: 的 `winload.efi`，displayorder 仅 `{current}`）
   —— 说明菜单不改系统 BCD，而是写 ESP 并注册 EFI 启动项。
2. **负向（不按 F10）**：重启后 Windows 正常进桌面；再启动程序，弹出「还原菜单未执行 /
   安装时间 2026-11-06 13:54:57，之后没有新的救援回执 / 可能原因：开机时没选 SysRecover 菜单项…」。
   —— 新增的"自证"提示能正确识别"没进去"。**通过**。
3. **正向（按 F10）**：F10 打开固件 Boot Manager，列表含独立项 `SysRecover`；选中后进入救援层，
   控制台输出 `RESTORE DONE: /dev/nvme0n1p3 (index 1)`（14:03:20）—— 救援层确实执行并完成了还原。**通过**。

附注：本次正向测试用的是"仅含 `Windows\System32\winload.exe/.efi`"的合成镜像，还原后系统盘被替换，
重启报 `0xc000000f`（`\Windows\system32\config\system` 缺失）。这是**合成镜像本身不含系统注册表**
的必然结果，不是还原链路缺陷；但也暴露出"安装源类镜像（如 install.esd）被当作可还原系统镜像"
的误判风险 —— 已在还原前增加目录表预检（见 `docs/07` 与对应提交）。
