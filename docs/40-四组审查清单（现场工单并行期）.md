## A 组：编号语义（ordinal / displayNo / partNumber）

结论先行：**三套编号没有跨到救援层**。conf 只写 `target_guid/offset/size/serial`
（`src/boot/task.cpp:105-108`），目标身份靠 offset+size+serial+GUID 定，不靠分区号。
`ordinal` 只用于显示与排序（`src/gui/main_form_restore.cpp:188,199,281`）。

| 编号 | 数据源 | 用途 | 是否落盘 |
|---|---|---|---|
| `partNumber` | GPT 槽位/MSR 序号（`src/disk/disk.cpp`） | 请求与校验（`main_form_restore.cpp:337`、`ops_boot.cpp:465`、`ops_staged.cpp:488`、`ops_returnold.cpp:405`） | 不落 conf |
| `displayNo` | 界面重排后的序号（`main_form_image.cpp:72`） | 屏幕显示 | 不落盘 |
| `ordinal` | 枚举顺序（`disk.cpp`） | 显示兜底、排序 | 不落盘 |

发现：

- **A1（P2）`disk 0 / part 1` 死兜底**
  `src/gui/main_form_restore.cpp:335-338`：选择无效时回落 `disk=0, part=1`。
  当前唯一调用方 `StartRestore` 已先校验（同文件 `94-95`），所以现在是死代码；
  但一旦新增调用点，会静默还原到“磁盘 0 分区 1”。建议无效即报错返回。

- **A2（P2）显示号与物理号可能不一致**
  `displayNo` 只在镜像页赋值（`main_form_image.cpp:72`）；还原页若没有该字段，
  显示退回 `ordinal`（`main_form_restore.cpp:188,199,281`）。自检日志/支持包目录名
  用的是物理号（`selfdiag.cpp:167-168` 的 `_dNpM`）。客服对照“用户说 2、日志说 3”
  会误判。建议日志同时打印 `displayNo` 与 `partNumber`。

- **A3（P2）Windows 侧重试的 serial 未归一化**
  `src/app/ops_staged_menu.cpp:321` 用 `W2U(d.serial) != serialS` 精确比较；
  救援层已放宽大小写/空白（`init:402-415`），Windows 侧没有。同一枚举源通常相等，
  但 conf 来自旧版本或手改时会误报“按契约找不到目标分区”。
  建议与救援层同一归一化口径。

- **A4（P3）partNumber==0 的防御缺口**
  `ops_returnold.cpp:405` 用 `partNumber` 严格匹配；0 永远匹配不到。正常分区非 0，
  属防御性问题。

- **A5（P3）界面序号未进 conf**
  目前“界面显示 2、物理 3”不会传到救援层，因为救援层不读分区号。保持现状即可；
  不要在 conf 里新增 `target_part`，否则反而制造第二套真值。

## B 组：`_ran` 判定与半途中断

判定链（当前工作区）：

- `_ran=1` 当且仅当 `/zjrestore-lite.sh` 可执行，且 **`/tmp` 里真有**任务日志或 conf
  （`init:1246-1255`，**[工单已覆盖]**）。
- `_ran=0` 时再看“交换中断现场”：`~old/Windows` + `~new/.zj-done` 同时在
  （`init:1317-1319`、`1345-1348`）。

### 状态矩阵

| 现场 | `_ran` | `_zb_hit` | 行为 | 数据安全 |
|---|---|---|---|---|
| 任务可读 + `~old` 在 | 1 | — | `triage_previous`（`_tp_has=1`），[2] 继续 | 安全 |
| 任务可读、无 `~old` | 1 | — | 直接跑脚本 | 安全 |
| 候选存在但一份都没读进 `/tmp` | 0 | 0 | “任务读不到”，10s 重启 | 目标未动 |
| 成功还原后只剩 `~old` | 0 | 0 | 一句“没有还原任务”，5s 重启 | 安全 |
| 交换中断：`~old/Windows` + `~new/.zj-done` | 0（日志已进 `~old`） | 1 | 三选一，[1] 需大写 YES | 安全 |
| 交换中断：`Windows` 还没移入 `~old` | 1（日志仍在根） | 0 | `triage` 在 `has_old_tree` 处直接返回；lite 重跑 swap → exit 3 → 失败菜单 | 旧系统可启动，安全 |
| 中断在 `rm -rf ~new` 末尾、`.zj-done` 尚存 | 0 | 1 | 误报“交换未完成”三选一 | 安全（回滚仍可用） |
| block 引擎断电（程序不在目标盘） | 1（软件目录 conf） | 0 | 失败菜单/可重试 | 安全 |
| block 引擎断电（程序在目标盘） | 0（conf 随格式化丢失） | 0 | “没有还原任务”自动重启，可能进入半写系统 | **缺真机条件** |

### 发现

- **B1（P2）早期中断不弹三选一**
  `has_old_tree` 只认 `~old/Windows`（`init:975,983`）。若断电发生在 `Windows`
  还没移入 `~old` 时，`triage_previous` 在 `init:1091` 直接返回。
  实际后果是 lite 重跑 swap 被 `~old` 存在拒绝（`zjswap.sh:85-90` exit 3），
  用户看到一次失败菜单再重启；旧系统仍完整。**不建议为此放宽 `has_old_tree`**，
  因为此时回滚也不可用（`~old` 不完整）。

- **B2（P2）删除阶段的假阳性**
  交换完成后 `rm -rf ~new`，若在 `.zj-done` 尚未删除时断电，`_zb_hit=1` →
  误报“发现未完成的交换”。建议收尾时**先删 `.zj-done` 再删其余内容**
  （或改名成 `.zj-done.del` 后删）；属 init 改动，交工单线执行。

- **B3（P1）fallback 不做身份校验（与工单改法冲突，请裁决）**
  `init:495-497`：只要首个候选 `cp` 成功就认作任务，**不校验 serial/guid/offset**。
  如果正确任务的日志因身份变化没被认定，而另一盘上存在旧日志副本，
  会把“错的契约”当任务运行；`target_offset` 相同的多盘机风险更高。
  建议：fallback 至少要求 serial 或 guid 之一匹配；两者都不匹配 → `_task_unreadable`，
  目标不动。若坚持“先能恢复优先”，至少首屏打印 fallback 身份并默认 [3]。
  详见第 6 节。

- **B4（P2）`find_old_part` 可能选到别的盘**
  `init:1089`：`TARGET_DEV` 为空时按设备枚举取第一个有 `~old` 的分区；
  多盘机可能选到与当前任务无关的旧备份，三选一文案指向错盘。
  建议 conf 里的身份与 `find_old_part` 交叉校验，或首屏打印设备名。

- **B5（P2）挂载失败静默**
  `has_old_tree`/`has_new_tree` 在 ntfs3/ntfs-3g 都失败时直接 `return 1`，
  只写 `/tmp/zj_n20.err`（`init:971-1013`）。dirty NTFS、BitLocker 下 PIT-249
  判定会漏，且屏上无提示。建议至少 `say` 一行“无法挂载，请人工确认”。

- **B6（P2）用户改名 exe 后软件目录 conf 失效**
  `conf_is_credible` 以 `SysRecover.exe`/`SysRecoverUI.exe` 文件名认定软件目录
  （`init:517-520`）。单文件版被改名为 `NineRestore.exe` 后，目标根 conf 若再丢失，
  任务就“读不到”。建议同时接受产品当前名，或以目录标记/版本文件认定。

- **B7（P3）`mark_pending_task` / `clear_stale_task` 返回值被忽略**
  `init:1135-1136`：回滚成功后即便标记没写盘也报“回滚成功”。对应 README 的
  “MBR 菜单需再运行程序恢复”这一已知限制，不算新问题，但建议记一行 WARN。

## C 组：UEFI 去重与 BootOrder

- **C1（P1）去重条件与注释不符：会删别的 ESP 的条目**
  注释写“只删同一块盘同一分区、描述和路径都一样”（`uefi.cpp:122-124`），
  实际去重只按“描述是我们 + 路径含 ZJRESTORE”（`uefi.cpp:1051-1066`）；
  `OptionHdMatches`（HD 起止 LBA + GUID）只用于 Windows Boot Manager（`uefi.cpp:1470` 附近）。
  双 ESP/双盘各装过 NineRestore 的机器，在 A 盘安装/升级会删掉 B 盘的固件项。
  **建议去重前加 `OptionHdMatches(当前 ESP)`**；这是用户可见的能力丢失。
  **【已修 · 证实方式/改法/前后差异见 §9.1】**

- **C2（P2）去重删除失败只记日志**
  `uefi.cpp:1066-1076`：`RemoveEntryNum` 失败写 `duplicate ... FAILED` 后继续，
  安装仍按成功返回；固件菜单可能仍两条，违背真机项 4。
  建议把该失败升级为安装状态降级（UI 可显示“需手动清理”）。

- **C3（P2）只清理 BootOrder 内的条目**
  `uefi.cpp:1053-1078` 只遍历 BootOrder；存在但不在 BootOrder 的孤儿 Boot#### 不会被清。
  部分固件菜单会列出全部 Boot####。建议安装后统计“我们”的条目数，或扫描 Boot0000-FFFF。

- **C4（P2）常驻安装的 BootOrder 写入无回读**
  `uefi.cpp:1129` 只检查 `SetVarW` 返回值；`UefiTempBootStateOk` 只覆盖临时项。
  界面刷新会读 NVRAM（`main_form_bootmenu.cpp:51`），所以用户最终能看到真实状态；
  但“安装成功”的即时提示可能被安全软件吞写。建议加一次 `UefiBootEntryExists` 回读。

- **C5（缺条件）0.9→1.0 的旧 UEFI 条目路径**
  `IsOurs` 要求设备路径含 `ZJRESTORE`（`uefi.cpp:257`）。若 0.9 的 ESP 目录名不是
  `ZJRESTORE`，升级后 `FindOurEntry` 找不到旧项 → 新旧两条。**需一台 0.9 真机确认**
  （真机项 4 的子项）。

- BootOrder 正常性（正面结论）：常驻项追加到末尾（默认仍进 Windows）；
  临时项提升到首位并保存 `bootorder.pre.bak`，`init` 进救援即归还（`init:1261-1271`），
  写后均有 payload 回读（`write_bootorder_payload`）。这部分不属“自证式回读”。

## 6. 需要裁决的一处冲突

**B3：救援层 fallback 是否必须做身份校验。**

- 工单线改法：保留“首个可拷候选即任务”的 fallback，靠 `WARN` 提示。
- 我的结论：**应改为 fail-closed**。理由：
  1. 本次工单的根因之一就是“身份不符被判成没任务”；修好归一化后，
     正确目标通常已被认定，fallback 只应在“真找不到”时兜底。
  2. fallback 候选可能来自另一块盘（旧软件目录、旧测试日志），
     `target_offset` 在多盘机首分区完全相同，会把镜像写到错盘。
  3. 错盘还原不可逆（block 引擎），代价远高于“多一次任务读不到”。
- 折中方案：fallback 只在 serial 或 guid 至少一项匹配时采用；
  都不匹配 → `_task_unreadable`，目标不动。若坚持保留，请在首屏
  打印 fallback 来源（设备名+serial+offset）并 120s 默认 [3]。

另一处**不建议改**：序列号归一化只做空白+大小写，不要扩展到剥离 `_`/`-`，
否则会把不同盘的序列号错误合并。

### 9.1 C1：UEFI 去重误删另一块 ESP —— 已证实，保留修复

**证实方式（静态可证 + 新增单测）**

- 旧判据：去重循环遍历全局 `BootOrder`，命中条件只有 `IsOurs(描述/路径含 ZJRESTORE)`，
  没有比较 HD 节点；`OptionHdMatches` 当时只用于 Windows Boot Manager 分支。
- 最小场景：两块 GPT 盘各有一个 ESP，且都装过 NineRestore；
  `BootOrder = [Boot0001(ESP A), Boot0002(ESP B)]`；在 ESP A 执行「安装菜单」
  （`ops_staged.cpp:1510` → `InstallUefiBootEntry`）。旧代码对 `Boot0002`
  只判 `IsOurs` 就 `RemoveEntryNum(2)`，ESP B 的固件项被删。
- 调用链上没有别的保护：`FindOurEntry` 只决定“复用哪个编号”，
  去重范围仍是全局 `BootOrder`；`RemoveEntryNum` 不知道 ESP。
- 执行级复现要写真实 NVRAM，本机不做（会改固件启动配置）——
  需双 ESP 真机/测试台，登记为缺条件。
- 已新增单测 `tests/unit_tests.cpp:uefi_dedup_same_esp_only`
  （纯判据、不碰 NVRAM）：构造只差 HD 节点的两份 `Boot####`，断言
  另一 ESP（GUID 不同）、LBA+1、size+1、截断数据均**不匹配**。
  按本轮“不自行编译”要求，该用例待统一构建时由 `tests.exe` 执行。

**改法**
