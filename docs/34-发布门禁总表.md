### 3.2 N15 结案：旧载荷为何一直留着（三选一结论）

用户口径（2026-11-07）："新软件不应受旧软件约束"。三个候选原因逐一给结论：

| 候选 | 证据 | 结论 |
|------|------|------|
| 打包没重建 | `Makefile:360` 的 `package` 只递归跑 `ARCH=x64/x86 all`（362/364 行），随后 `Makefile:380` 把 `bootfiles/initramfs-zjrestore.cpio.gz` **原样 copy** 到 `dist/bootfiles/`；该 initramfs 只由手工脚本 `tools/vmtest/build-alpine-initramfs.py`（输出在 341 行）重建，**Makefile 没有任何依赖/前置规则**。旧 dist 的内嵌载荷因此停在 11-02（17,389,826 B） | **是主因** |
| 安装时没覆盖 | `InstallUefiBootEntry` 按"源 CRC vs 盘上 CRC"决定 keep/copy；旧 dist 的源就是旧载荷，盘上也是旧载荷 → 命中 keep，日志只写"不变"，没有任何"盘上是哪版"的自证。新 dist 实机安装后 ESP 从 17,389,826 B 变为 17,391,321 B，证明覆盖逻辑本身有效 | 不是独立原因；是"旧源 + keep"把主因藏了起来 |
| 写入了但启动项仍指旧文件 | 启动项目标路径固定为 `\EFI\ZJRESTORE\vmlinuz-zjrestore.efi`；新旧载荷同名同路径，覆盖后同一启动项即加载新码（实机：`rescue-build.txt` 变 `1.0.0-beta.1`，进救援后行为符合新脚本） | 不成立 |

**结论**：旧载荷残留的唯一自洽解释是**打包链没重建 initramfs**（N10/C6），安装器再把"旧源=旧盘"判成 keep。
产品侧修复：C6（`b82af8f`）拦截旧 dist；N17（`6d239e8`、`61680a1`）在下发前自证 ESP 版本，旧版不再被静默沿用。

## 5. 两条新发现的缓解方案与代价评估

### 5.1 N7：固件静默回落（选了我们却回到 Windows，且我方零记录）

**现状**：固件 Boot Manager 的加载失败（安全启动拒绝、设备路径失效、ESP 被改、NVRAM 项被清）
由固件自行回落到下一项，**不会通知任何 OS 侧代码**。所以"按了 F10 选了 SysRecover 又回到 Windows"
在我们这边表现为"什么都没有发生"。

**已落地的缓解（成本≈0，已在上游提交）**：
- `entry-started`（`cf2c454`）：init 在动任何分区前，向 ESP `EFI/ZJRESTORE/entry-started.txt`
  追加一行（时间戳 + kernel + build + boot_id），失败静默、不阻塞启动，保留最近 50 行。
- 配套门禁 C4（`tools/check-shell.py`）：断言标记函数存在、在首次调用 `zjrestore-lite.sh` 之前执行、
  只写该文件、函数体内无 `exit`。
- **判读**：没有这一行 → 固件没加载我们的 EFI / 内核没起来；有这一行无后续日志 →
  init 起来了、卡在后段（日志只落内存会随重启丢失）。

**局限**：仍是"内核起来之后"的标记，无法把"固件跳过"与"内核崩溃"分成三态。

**根治方案（自建 EFI shim，暂缓）**：

| 项 | 评估 |
|---|---|
| 做法 | 一个最小 UEFI 应用（`EFI/ZJRESTORE/zjmark.efi`），经 `EFI_SIMPLE_FILE_SYSTEM` 往 ESP 写一行"shim-started"，再用 `LoadImage/StartImage` 链到现有内核（或现有 shim/grub 链） |
| 代码量 | 约 300–600 行 C（EFI 文件系统读写 + 文件路径拼接 + chainload + 失败兜底），外加独立编译目标与打包规则 |
| 工作量 | 实现 2–3 人日；验证 2–3 人日（UEFI 直启 / Secure Boot 开与关 / 4Kn ESP / 老固件 / 双架构包），合计约 **1 周** |
| Secure Boot | 未签名 shim 在 SB 开启时会被固件拒绝——等于把"静默回落"提前到我们自己的 shim，仍需签名或 MOK 注册才能闭环；免费签名渠道不可控，这是主要风险 |
| 运行风险 | 多一跳 = 多一个可失败环节（ESP 写失败、LoadImage 失败、路径大小写）；救不回时现象与现状相同（依旧回落），但至少能留下标记 |
| 结论 | **暂缓**。先用 `entry-started` + 用户材料判三态；只有实机反复出现"无标记"且需要归因固件时再开工 |

### 5.2 N8：diag 缺"用户实际选过哪一项"的证据

**现状**：固件 Boot Manager 的菜单选择完全在固件里，我方代码看不到；diag 支持包里只有
Windows 侧日志、`logs/collected`、`boot-cleanup.log`，无法回答"用户到底点了哪一项"
（尤其临时项与常驻项都叫 SysRecover 时）。

**缓解（零代码，先执行）**：要求用户提供四样材料——
1. 程序内「打包日志」导出的支持包（含 `logs\collected`、`boot-cleanup.log`、`menu-install.txt`）；
2. F10 / 固件 Boot Manager 的**首屏照片**（能看清列表里有几项、名字与顺序）；
3. `EFI\ZJRESTORE\` 文件清单（尤其 `entry-started.txt` 是否存在、最后一行时间）；
4. `bcdedit /enum firmware` 文本（确认 `BootOrder` 与临时项是否仍在）。

判读顺序：`entry-started` 无 → 固件/内核层；有、无后续 → 救援层后段；
`menu-install.txt` 时间对不上 → 装的是旧菜单；`BootOrder` 里没有我们的项 → 启动项被清掉。

**可选代码增强（成本 0.5–1 人日，列入观察期）**：
- 安装侧给常驻项与临时项的 kernel 命令行各加一个标识（如 `zjentry=menu` / `zjentry=temp`），
  init 写标记时把它带进 `entry-started.txt`。这样至少能区分"哪**类**启动项"。
- 但"用户在固件菜单里点了第几行"仍只能靠照片——固件不向我们暴露选择事件，
  除非自建 shim 且 shim 能拿到 `LoadOptions`（仍不保证）。

**代价结论**：先走材料清单（零成本、可立即执行）；命令行标识增强成本低、收益中等，
放观察期；不为此改固件交互模型。

### 5.3 N13：完整系统 ESD 被误判"版本不受支持"（逐条判据复算）

用户镜像 `D:\Software\System\20260927Win11不忘初心26H2_26300.9711.esd`（1.81 GB），
按 `src/wim/wim_precheck.h` 的 11 条判据逐条复算，**只有第 2 条不满足**：

| # | 判据 | 实际读到 | 结果 |
|---|---|---|---|
| 1 | 魔数 `MSWIM\0\0\0` | 一致 | PASS |
| 2 | **版本** | `version=0x00000E00`（固态 ESD） | **FAIL（唯一）** |
| 3 | 头长度 148..4096 | `cbSize=208` | PASS |
| 4 | 文件 ≥ 头长度 | 1.81 GB | PASS |
| 5 | 至少 1 个子镜像 | `imageCount=2` | PASS |
| 6 | 资源表不越界 | xml(4930,1814469138)、bm(0,0)、int(0,0) | PASS |
| 7 | XML ≤ 256 MB | 4.9 KB | PASS |
| 8 | XML 可读 | 4930/4930 字节 | PASS |
| 9 | XML 可解析 | `<WIM` 与 `</WIM>` 都在 | PASS |
| 10 | XML 子镜像数 = 头部 | 2 = 2 | PASS |
| 11 | 完整性表 | size=0/off=0（未写） | PASS（原判据会误杀，已删） |

根因：`version` 不是"主版本左移 16 位 + 次版本"。wimlib 只写 `0x00010D00`（普通 WIM）
与 `0x00000E00`（固态 ESD）；后者按 `>>16` 算得 0，被判 `major<1`。
0.9.96 没有这段预检，所以同一镜像能装菜单。

修复后的实测（`c6bc981` 产物，直接读真实文件）：
- 上述镜像 `QuickPrecheck rc=0`；`\Windows\system32\winload.exe` = 在、
  `\Windows\System32\config\SYSTEM` = 在 → `ClassifySystemImage` 判 ok；
- `20260612Win10…19045.7417.esd`（同为 0xE00）同样 ok；
- 单测 `wim_precheck_accepts_full_system_esd`、`wim_precheck_ignores_optional_integrity_offset`、
  `wim_precheck_blocks_corrupt_header_size`、`system_image_kind_*` 四条覆盖
  ①完整系统镜像通过 ②安装源被拒 ③结构损坏被拒 ④查询失败放行。
