### 3.2 N15 结案：旧载荷为何一直留着（三选一结论）

用户口径（2026-11-07）："新软件不应受旧软件约束"。三个候选原因逐一给结论：

| 候选 | 证据 | 结论 |
|------|------|------|
| 打包没重建 | 旧 `package`（现 `Makefile:385`）只递归跑 `ARCH=x64/x86 all`，随后把 `bootfiles/initramfs-zjrestore.cpio.gz` **原样 copy** 到 `dist/bootfiles/`（现 `Makefile:405`）；该 initramfs 只由手工脚本 `tools/vmtest/build-alpine-initramfs.py` 重建，旧 Makefile **没有任何依赖/前置规则**。旧 dist 的内嵌载荷因此停在 11-02（17,389,826 B） | **是主因** |
| 安装时没覆盖 | `InstallUefiBootEntry` 按"源 CRC vs 盘上 CRC"决定 keep/copy；旧 dist 的源就是旧载荷，盘上也是旧载荷 → 命中 keep，日志只写"不变"，没有任何"盘上是哪版"的自证。新 dist 实机安装后 ESP 从 17,389,826 B 变为 17,391,321 B，证明覆盖逻辑本身有效 | 不是独立原因；是"旧源 + keep"把主因藏了起来 |

### 3.4 N18 防复发：救援载荷"过期即失败"（提交 `4b7f337`、`5ca5b1c`）

### 3.5 N19 主窗置后取证（三选一结论：**已确认为缺陷，时序相关**）

**取证范围（2026-11-07，静态）**：全仓检索 `SetForegroundWindow` / `BringWindowToTop` /
`SetWindowPos(HWND_TOPMOST/NOTOPMOST)` / `ShowWindow` / `SetActiveWindow` / `SetFocus` /
`SetWindowPos` / `ShellExecute*` / `CreateProcessW` / `WinExec` / `system`，逐个核对触发时机、
owner、返回值与失败回退。

**结论**：现象**真实存在**，但由两类不同来源造成 ——

1. **设计内（可稳定复现）**：4 处主动把资源管理器/浏览器带到前台；用户点了「日志/导出驱动」
   或救援失败提示里的「打开日志」后，主窗必然退到 Explorer 之后。这不是 Z 序 bug，而是
   "打开外部窗口"的预期结果，但用户会感知为"软件自己沉下去了"。
2. **缺陷（时序相关，偶发、难复现）**：三个自绘模态框关闭后只调用
   `SetForegroundWindow(owner)`，**返回值被忽略**，也没有 `BringWindowToTop` /
   `SetWindowPos(HWND_TOP)` 回退；当前台锁（Explorer/其它进程刚抢到前台）导致调用失败时，
   主窗就留在后面，且**无日志、无提示**。这与用户"试了几次又没出现"的形态一致。

### 3.6 N21（2026-11-07 新发现）：Secure Boot 模式下一次性启动项**不会失效**，可能反复进救援

**状态：已修（N20 批 1，2026-11-07），QEMU/OVMF 实测通过。**

- 根因（静态取证）：解除条件只认 `zjtemp`（旧 `init` 用 `grep -q 'zjtemp'` 判断 Boot####
  是不是我们的临时项；lite 只删 `EFI/ZJRESTORE/vmlinuz-zjtemp.efi`）。而 `Grub` 模式
  临时项指向 `\EFI\ZJRESTORE\shimx64.efi`，描述为 `SysRecover Temporary Restore`，
  变量内容里没有 `zjtemp` → 判定失配、BootOrder 不还原 → 反复进救援。
- 修复（与 N20 同一处）：`is_our_temp_entry` 不再 grep 文件名，改为按描述/路径标记匹配；
  且因为 Boot#### 变量是二进制（描述为 UTF-16LE），`tr -d '\000'` 在 busybox 下不可靠，
  改成 `od -An -tx1` 打十六进制串后匹配 `SysRecover…` / `ZJRESTORE`（ASCII 与 UTF-16LE 都认）。
- 实测证据见 §4.1 第 10 项。

- 修复前取证（保留供审计）：
  - 解除条件只认 `zjtemp`：旧 `init` 用 `grep -q 'zjtemp'` 判断 Boot#### 是不是
    我们的临时项；lite 只删 `EFI/ZJRESTORE/vmlinuz-zjtemp.efi`。
  - `Grub` 模式下临时项根本没有 `zjtemp`：`src/boot/uefi.cpp:579-594` 的临时项 `targetPath =
    \EFI\ZJRESTORE\shimx64.efi`，文件集是 shim + `grubx64.efi` + `grub.cfg` + `vmlinuz-zjrestore`
    （`uefi.cpp:585-592`）；描述为 `kTempEntryDesc`（`src/boot/bootnames.h:10`）
    `SysRecover Temporary Restore`，变量内容里没有 `zjtemp`（`zjtemp` 只在 `None` 模式的
    `uefi.cpp:615-618` 出现）。
  - 结果：判定走 "does not look like ours, left alone" → `restore_bootorder` 被跳过 →
    BootOrder 仍以该临时项开头；`reboot_now` 再兜一次，结论相同；lite 侧同样什么也没删。
  - 第二次启动：固件仍先到 shim → grub → init；`_ran=0` → "no restore task" → 10 秒后重启 →
    又回到同一临时项 → **无限救援循环**，Windows 首启清理永远没机会运行。
  - 影响面：Secure Boot 开启（默认 `Grub`）+ 一次性条目（没装常驻菜单）的日常还原。**这是
    PIT-197 在现场修过的同一症状，只是换到 SB 链后判定条件失配而复发。**

## 5. 两条新发现的缓解方案与代价评估

### 5.1 N7：固件静默回落（选了我们却回到 Windows，且我方零记录）

**现状**：固件 Boot Manager 的加载失败（安全启动拒绝、设备路径失效、ESP 被改、NVRAM 项被清）
由固件自行回落到下一项，**不会通知任何 OS 侧代码**。所以"按了 F10 选了 SysRecover 又回到 Windows"
在我们这边表现为"什么都没有发生"。

**已落地的缓解（成本≈0，已在上游提交）**：
- `entry-started`（`cf2c454`）：init 在动任何分区前，向 ESP `EFI/ZJRESTORE/entry-started.txt`
  追加一行（时间戳 + kernel + build + boot_id），失败静默、不阻塞启动，保留最近 50 行。
- 配套门禁 C4（`tools/check-shell.py`）：断言标记函数存在、在首次调用 `zjrestore-lite.sh` 之前执行、
  只写该文件、函数体内无 `exit`。
- **判读**：没有这一行 → 固件没加载我们的 EFI / 内核没起来；有这一行无后续日志 →
  init 起来了、卡在后段（日志只落内存会随重启丢失）。

**局限**：仍是"内核起来之后"的标记，无法把"固件跳过"与"内核崩溃"分成三态。

**根治方案（自建 EFI 标记程序）：2026-11-07 只读事实核查（不改代码）**

**先回答用户的原疑**：现有 Secure Boot 链**没有任何签名问题**——链上每个可执行文件都是 Debian
已经签好的（零注册、零交互，VM 已实测，见 `docs/07`）。"签名问题"只出现在**我们自己新写一个
EFI 程序**时：安全启动信任的是"哪把证书签了它"，不是"软件属于谁"。Debian 的签名章借得到
（我们用它的 shim/GRUB/内核），但拿不到 Debian 的私钥；微软也不会自动给我们新写的程序盖章。

**1. 包里带的 shim 是什么（实测）**

- `bootfiles/sb/shimx64.efi`：**Debian 的 shim 16.1**（未修改），
  `$Version: 16.1`、SBAT `shim.debian,1,Debian,shim,16.1,https://tracker.debian.org/pkg/shim`。
- PE 证书表位于 `0x105188`（文件偏移 1,069,448），表长 19,368 B，**两条 PKCS#7 签名**：
  - 第 1 条：Subject `Microsoft Windows UEFI Driver Publisher` ← Issuer `Microsoft Corporation UEFI CA 2011`
    ← Root `Microsoft Corporation Third Party Marketplace Root`；叶证书有效期 `2026-03-12 → 2026-06-26`。
  - 第 2 条：Subject `Microsoft UEFI CA 2023 signer` ← Issuer `Microsoft UEFI CA 2023`
    ← Root `Microsoft RSA Devices Root CA 2021`；叶证书有效期 `2025-07-24 → 2026-07-23`。
  - 即"**微软 CA2011 + CA2023 双签**"（`docs/06` §5 的说法与实测一致）。
- 上述两张微软叶证书**在 2026-07 已过期**。UEFI 安全启动按 db/dbx 信任判定、不做有效期检查，
  所以仍能启动；真正的长期风险是 **dbx/SBAT 撤销**（shim 的 SBAT 为 `2025021800`），不是日期。

**2. shim 之后靠什么信任（内置证书，不是 MOK）**

- shim 二进制内含 `Debian Secure Boot CA` 与 `Debian Secure Boot Signer 2022 - grub2` 的证书串，
  其二级镜像 `grubx64.efi` 正是由 `Debian Secure Boot CA` 签发 → **shim 直接信任它，无需 MOK 注册**。
- 因此本产品当前这条线**不会弹蓝底 MOK 界面**，代码里也没有面向用户的 MOK 提示
  （`ZJ_ENABLE_MOK_PATH=0`，`src/boot/uefi.cpp:33`）。
- 仓库里**没有** `zj-mok.cer`、`zjrestore-uki.efi`，也没有 `keys/` 目录（本机实测 `Test-Path keys` = False）；
  也就是说 MOK 备选线**连资产都不在本环境**，要启用必须先重建密钥与 UKI。

**3. `uefi.cpp` 的 SbMode 分支（`src/boot/uefi.cpp:553-620`，`1459-1482`）**

| 模式 | 触发 | 随包下发 | 启动项 target | OptionalData |
|---|---|---|---|---|
| `None` | Secure Boot 关（`CurrentSbMode()` 直接返回 None） | `vmlinuz-zjrestore.efi` + `initramfs` | 直指内核 | `kCmdLine`（`initrd=… console=tty0 nvme_core.io_timeout=1 zjre=1`，`uefi.cpp:67-69`） |
| `Grub`（SB 开启时默认） | `sb-mode.txt` 未指定或未知 | `shimx64.efi` + `grubx64.efi` + `grub.cfg` + 内核 + initramfs | `\EFI\ZJRESTORE\shimx64.efi` | 空（命令行在 `grub.cfg`） |
| `Shim`（编译时关闭） | `sb-mode.txt=shim` 且 `ZJ_ENABLE_MOK_PATH=1` | shim + `mmx64.efi` + `fbx64.efi` + 我们的 UKI（改名 `grubx64.efi`）+ `zj-mok.cer` | shim | 空 |
| `Bootapp`（实验） | `sb-mode.txt=bootapp` | `efiloader.efi`（**未签名**）+ `zjrestore-uki.efi` | BCD bootapp，非固件项 | — |

**5. 新增自有 EFI 程序挂在 shim 之后，是否需要微软签名**

- **需要**。shim 只做一件事："下一个文件是不是我内置证书 / 用户 MOK / db 里的证书签的"。
  它不会把签名权转交给我们，也不会给我们盖章。我们自签的程序要进这条链，只有三条路：
  1. **用户一次性 MOK 注册**（免费；首次重启进蓝底 MokManager，选 `Enroll key from disk` →
     `zj-mok.cer` → 确认；之后零交互）。代价：一次用户操作 + 我们重建密钥/UKI（约 1 周，
     且 `mmx64.efi` 当前是 Canonical 的，与 Debian shim 的搭配需重验——仓库资产是混来源的）。
  2. **把我们的证书写进固件 db**（免费但更麻烦，各品牌 BIOS 路径不同，且可能被固件 UI 拦住）。
  3. **微软 UEFI CA 送签**（可做到零交互，但要提交审核/走流程，不能算"不额外花钱"）。
- 因此对"N7 根治是否可以走 shim 之后、不额外花钱"的回答是：**需要用户做某种一次性操作**
  （MOK 注册）；"免费"与"零交互"不能同时成立。这不影响 1.0 的现有能力——现有链依然是
  Debian 盖章、零注册零交互。
- 另一个不新增 EFI 程序的低成本缓解是"在 `grub.cfg` 里留痕"（GRUB 已起来 → 写标记），
  理论上能把"固件没到 grub"与"grub 起来了"分开；**未验证 GRUB 能否在 ESP 上写文件，
  本轮不承诺**。若用户愿意，可作为 N7 的下一候选（成本远低于 300–600 行 EFI 程序）。

**结论（写入口径）**：N7 维持**暂缓**；在 `docs/33` 面向用户写清"现在的 Secure Boot 链零注册，
签名问题只涉及我们未来自建的程序；要免费就得用户一次性注册，要零操作就得送微软"。不在 1.0
修复范围内。

### 5.2 N8：diag 缺"用户实际选过哪一项"的证据

**代价结论**：先走材料清单（零成本、可立即执行）；命令行标识增强成本低、收益中等，

### 5.3 N13：完整系统 ESD 被误判"版本不受支持"（逐条判据复算）

### 5.4 N20：尽早归还启动顺序 + Windows 侧"未完成"感知（批 1 + 批 2 已实现）

> 批 1（①②③ + N21）与批 2（④=A，范围锁死）均已落地；结论与实测见 §4.1 第 10 项，
> 批 2 标记的写入/删除审计见 §5.4.9。

**先纠正一个前提**：代码里 disarm 本来就发生在**开工前**，不是"完成才 disarm"——
`bootfiles/alpine/init:738` 在调用 `zjrestore-lite.sh` 之前就执行 `disarm_staged_entry`，
`reboot_now`（`init:679`）再兜一次。用户看到的"只有完成才失效"是 §3.6 的 N21：SB（grub/shim）
模式下这段判定失配、**什么都没做**，于是临时项一直留在 BootOrder[0]。所以 N20 不是在
"把 disarm 提前"，而是把已有的意图做成"可验证 + 可回退"，顺带修掉 N21。

#### 5.4.1 救援流程是否单次启动可完成（问题 1）

- **正常路径是单次的**：lite 结尾自己 `reboot -f`（`init:780-782` 兜底），中途没有"重启再继续"的
  正常设计。
- **但存在跨启动续做状态**，早 disarm 会丢掉入口：
  - `~new\.zj-undo-phase`：returnold 反向交换被打断后，下次进救援继续（`init:489`、
    `zjrestore-lite.sh:859-861`）；
  - `~new\.zj-done`：A 引擎 swap 的"可交换"前提（`zjrestore-lite.sh:197-199`），swap 前崩溃需重进；
  - B 引擎"已格式化未 apply"可安全重跑（`zjrestore-lite.sh:622` 的 STEP 编码）。
- **结论**：不能"早删"，只能"早重排 + 保留重入入口"；否则一次断电/崩溃就把续做能力弄丢。

#### 5.4.2 早 disarm 的插入点与失败语义（问题 2）

- **权威插入点**：`bootfiles/zjrestore-lite.sh:130-140`（`contract_version` 校验通过）之后、
  第一个破坏性动作之前（swap 在 `1261` 起，B 引擎 prepare/apply 在 `1321` 之后）。此时已确认
  "契约可读、目标设备可定位"，且还没碰目标盘。
- **兜底插入点**：保留 `bootfiles/alpine/init:738`（幂等），以及 `reboot_now`（`init:679`）。
- **失败语义：中止（用户 2026-11-07 拍板，批 1 已实现）**：写 NVRAM 失败 → 屏幕报错 +
  求助渠道，**不写目标盘**并关机/重启。理由：带着"用户可能被困"的状态继续还原，
  风险大于收益；`reboot_now` 里再兜一次（幂等）。

#### 5.4.3 归还到什么状态（问题 3）

| 方案 | 做法 | 新系统首启崩了会怎样 |
|---|---|---|
| A. 还原 `bootorder.pre.bak` 原序 | Windows Boot Manager 回到第一位 | 固件找不到可启动项时可能直接进 BIOS/报错；**不保证**回落到救援 |
| B. 临时项降到 BootOrder 末位 | Windows 第一，救援仍可手动选 | 用户能进救援；但每次开机都多一项，且"临时"名不副实 |
| **C. 混合（推荐）** | 原序在前 + **一个新常驻 `SysRecover Recovery` 项固定在末位**；确认它可用后，才删临时项与 `vmlinuz-zjtemp.efi` | Windows 起不来时，用户可从固件菜单选 Recovery 进救援；首启成功后由 Windows 清理助手删 Recovery 项 |

- 选 C 的成本：`Grub` 模式本来就常驻一整套 shim/grub/内核，新增≈0；`None` 模式需保留
  `vmlinuz-zjrestore.efi`（约 12 MB），ESP 预检已是 fail-closed，空间不够会提前拒绝。
- Recovery 项必须与"临时项""常驻菜单"三者描述/GUID 都不同，避免首启清理误删。

- 用户 2026-11-07 拍板 ②：采用"`bootorder.pre.bak` 原序在前 + **已有救援项**追加到末尾"，
  不设 BootNext、不新建 C 方案的 `SysRecover Recovery` 项（①=B 保留现有救援项）。

#### 5.4.4 新系统首启失败（问题 4）

- **现在就有**：`~old` 保留到首启成功；首启 helper 写 `%ProgramData%\SysRecover\boot-cleanup.done`
  的 `ok=1/ok=0`（`cleanup_marker.h:14-17`）；救援层可凭 `~new\.zj-undo-phase` 续做 returnold。
- **要新增**：
  1. 5.4.3 的 Recovery 项（保证"新系统起不来"时还有入口）；
  2. 救援层开机自检：发现 `~old` 存在且 `boot-cleanup.done` 缺失/非 `ok=1`，首屏给
     `[1] 回滚到旧系统（returnold） [2] 再试新系统 [3] 仅重启`（复用现有 returnold 引擎）；
  3. 回滚成功后按 N21 修正后的 disarm 真正归还 BootOrder。
- **不可行**：Windows 完全起不来时，Windows 侧无法弹任何提示或执行回滚——所以"一键回滚"
  只能在救援层，Windows 侧只负责"告知 + 指引"。

#### 5.4.5 Windows 侧三态判定（问题 5）

| 状态 | 判定依据（按顺序） | 用户看到的一句话 | 一键回滚 |
|---|---|---|---|
| ① 没进救援 | ESP `EFI/ZJRESTORE/entry-started.txt` 无本次新行；各盘根无新 `ZJRESTORE-status.txt` | 「没有检测到本次还原的执行记录（可能未进入救援层，或已取消）。/ No rescue run was recorded.」 | 否 |
| ② 进了没完成 | `entry-started.txt` 有本次 boot 行；`ZJRESTORE-status.txt` 的 `result` ≠ `OK`（或只有 `zjrestore-boot.log`） | 「上次还原没有完成（step=…）。可以重新发起还原，或打开诊断包。/ Last restore did not finish (step=…).」 | 否（提供"重试"） |
| ③ 完成了但新系统没起来 | `result=OK`，但 `boot-cleanup.done` 缺失或非 `ok=1`，且 `~old` 仍在 | 「还原已完成，但新系统首次启动没有成功；请从救援层回滚到旧系统。/ Restore finished, but the new system never completed its first boot; roll back from rescue.」 | 是（入口在救援层；Windows 侧只给指引） |

- **现状缺口**：RunOnce 目前只注入**新系统**（`ops_staged.cpp:1050-1060`、
  `ops_inplace.cpp:543-595`），旧系统没有钩子。N20 要在"创建任务时"往**当前运行的系统**
  注入一次性检查（A 引擎有旧系统可用；B 引擎原地重装没有旧系统，只能靠新系统 RunOnce +
  Recovery 项）。检查器只读 ESP/盘根/ProgramData，不动盘。

#### 5.4.6 改动清单（设计记录；实际实现以 §4.1 第 10 项为准）

1. `src/boot/uefi.cpp`：新增 `InstallRecoveryEntry`（常驻末位、独立 desc/GUID）与
   `ReorderBootOrderWindowsFirst`（读 `bootorder.pre.bak`，Windows 优先、Recovery 末位）。
2. `bootfiles/alpine/init`：N21 判定修正（按 `temp-entry.txt` 的条目号，而不是 `zjtemp`）、
   `hand_back_bootorder`（只重排不删载荷）、首屏 `~old`/cleanup 自检菜单。
3. `bootfiles/zjrestore-lite.sh`：契约校验后调用 `hand_back_bootorder`；`disable_staged_entry`
   改为"确认 Recovery 可用后再删临时载荷"。
4. `src/app/ops_staged.cpp` / `ops_returnold.cpp`：任务创建时往旧系统注入 `ZJAFTERRESCUE`

5. `src/app/ops_inplace.cpp` / `cleanup_marker.h`：首启 helper 只在 `ok=1` 时删 Recovery 项。

#### 5.4.7 失败矩阵

| 场景 | 行为 |
|---|---|
| 契约缺失/版本不匹配 | 不动目标盘；归还顺序（尽力）后重启（现状不变） |
| NVRAM 重排失败 | 继续还原；status 记 `bootorder=FAILED`；末屏提示进 BIOS；不静默 |
| Recovery 项安装失败（ESP 满/只读） | **fail-closed**：不删临时项（保留重入能力），继续还原，并提示 |
| 首屏回滚（returnold）失败 | 保留 `~old`，给专家 shell/重启（沿用现有失败菜单） |
| 旧系统钩子被用户清掉/换机 | 落到状态①文案；不影响还原 |
| 早归还后中途断电 | 下次开机进旧 Windows（状态②提示）；要继续任务需从固件菜单选 Recovery |

#### 5.4.8 风险与不可行点

- 早归还后**自动续做不可能**：固件不会自己再选救援；续做必须用户手动选 Recovery。这是设计取舍，
  `docs/33` 要写清。
- 固件"挑食"时 Recovery 项只能保证"手动可选"，不能保证自动回落（N7 的同一限制）。
- 状态③的一键回滚无法在 Windows 侧实现（Windows 没起来）。
- 需要新快照做三组 VM 验证：中途杀进程后重启回 Windows / 再进救援续做 / 首启失败回滚。

#### 5.4.9 批 2 标记审计（只写了什么 / 写在哪 / 什么时候删）

- **只写什么**：一个文本文件，三行 `status=unfinished`、`when=YYYY-MM-DD HH:MM:SS`、
  `action=rollback`。不写注册表、不写 RunOnce、不新增/修改启动项、服务或计划任务。
- **写在哪**：`<旧系统根>\ProgramData\SysRecover\last-task-unfinished.txt`
  （救援层在 `triage_previous` 回滚成功、`zjswap-undo.sh` 返回 0 之后写入；
  挂载/写入失败只 WARN，不阻塞回滚）。
- **什么时候删**：Windows GUI 每次正常启动，`StartupLazyWork` 末尾投递 `WM_CHECK_RESCUE`，
  `TakePendingTaskMarker` 读取后**立即删除**该文件（读即自删；即使提示未能弹出也已删除）。
  删除后不会再出现第二次提示。

**结论**：方向可行，但必须**先修 N21**（否则早归还全是空转），且早归还是"重排 + 保留救援项"
而不是"删除"。批 2 已按用户决策 ④=A 实现并实测，本节保留设计记录。
